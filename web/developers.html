Developer guide

How the code is arranged, where to put a new feature, and how to get a server running — on your laptop, or somewhere your friends can reach.

The shape of it

A Python game engine with a thin web front end. The server is authoritative: the browser never decides anything. It sends an intent ("I want to roll"), the engine validates it against the current state, and every client gets back a list of events plus a fresh snapshot. One server runs one game at a time.

The five things worth knowing before you start

  1. rules.apply() is the only door in. Every action is (name, payload) → a handler in _INTENTS → (new_state, events). Handlers mutate state in place, so apply runs them against a deep copy and returns that. A handler that raises therefore discards its half-finished work, and the caller's game is untouched.
  2. Events are the narration; the snapshot is the truth. Events drive toasts and the log. The snapshot drives everything else. If a client needs to know something, it belongs on the snapshot.
  3. data/board.json is data, not documentation. Everything in its rules block is read by the engine. If you add a key there, add it to BoardRules in board_schema.py and read it somewhere — an undeclared key validates fine and does nothing, which is worse than an error.
  4. The state models forbid unknown fields. That catches typos, at the cost of making the save file fragile. Removing a field is survivable — the loader retries once, dropping keys the schema no longer knows — but renaming one silently loses its value. Copy saves/current_game.json aside before touching state.py.
  5. The client is a mirror, never an authority. Where the UI decides whether to offer a button, it is duplicating a server rule, and the two must agree. The card-play windows (POST_ROLL_PLAYABLE_EFFECTS and friends) exist in both rules.py and controls.ts for exactly this reason, and each names the other.

Where to add things

You want to…Go to
Add a new card Add the entry to data/tower_cards.json or raven_cards.json with an effect_key. Write a @register("your_key") handler in cards_effects.py. Add player-facing copy to ui/card_descriptions.ts and artwork to ui/card_art.ts. If it needs a play window or player input, wire it in controls.ts.
Add a square that does something Give the space an action in board.json, then handle its key in _dispatch_space_action (rules.py). Unknown keys log unhandled_space_action rather than failing silently.
Add a new player action Write _intent_your_thing in rules.py, register it in _INTENTS, and send it from controls.ts. The /ws router picks up anything in _INTENTS automatically.
Change how movement works movement.py for what counts as a legal destination; board.py for the graph search underneath it. reachable() is memoised on the board, so it is safe to call repeatedly.
Change the board data/board.json. The scripts in tools/ are one-off authoring helpers — read before reusing.
Add a stat Lifetime stats: stats.py plus _update_stats_from_events in main.py. End-of-game stats: GameStats in state.py plus compute_game_stats in rules.py, which folds the event log rather than counting as it goes.
Change what players can see of each other net/redact.py.
Write the test first — they are cheap here. The engine is pure enough that most rules can be tested in a dozen lines with a hand-built GameState, and the whole suite runs in well under a second. Look at tests/test_rack_pardon_and_traps.py for the house style.

Running it

First time

conda create -n outrage python=3.12 -y
conda activate outrage
pip install -e .

cd web && npm install

Day to day

Two terminals. The backend:

conda activate outrage
uvicorn server.main:app --reload --port 8000

and the front end, which proxies /ws and /api to it:

cd web && npm run dev

Open localhost:5173. Vite reloads the UI on save; --reload restarts the engine.

--reload plus a change to state.py is how you lose a game in progress. The server re-validates saves/current_game.json on every restart. Back it up before touching the state models, and check it still loads afterwards.

Tests and types

python -m pytest tests/ -q      # the rule engine
cd web && npx tsc --noEmit      # the front end

The test suite redirects the save files to a temporary directory and asserts afterwards that the real saves/ was untouched, so running it can never eat a live game.

One process, both halves

Build the front end and the backend serves it, so there is only one port to think about. This is what you want for actually playing: 

cd web && npm run build
cd .. && uvicorn server.main:app --host 0.0.0.0 --port 8000

Everything is then on port 8000 — the game at /, these pages at /about, /rules and /developers.

Playing with people elsewhere

--host 0.0.0.0 makes the server reachable from other machines. On the same network, that is all you need: find your machine's LAN address and send people http://<your-ip>:8000.

To play with people who are not on your network, put a tunnel in front of it:

# Cloudflare — no account needed for a throwaway URL
cloudflared tunnel --url http://localhost:8000

# or ngrok
ngrok http 8000

# or Tailscale, if everyone is already on your tailnet
tailscale serve 8000

Each prints a public URL. Send it round, everyone picks a username, and the first person to press Start game starts it.

There is no authentication. Anyone with the URL can join, chat, act as themselves, and end the game. Usernames are claimed on a first-come basis, and reconnecting is done by typing the same name — so anyone who knows a player's name can take over their seat. That is fine for a link you send to five friends for an evening; it is not fine for a URL you leave running in public. Take the tunnel down when you are finished.

Saves

saves/current_game.json holds the live game and is rewritten after every action, so a restart picks up where you left off — including the RNG state, which is why a saved game replays identically. saves/stats.json holds lifetime per-username tallies. Delete either to reset it; a file the server cannot read is renamed .bak rather than being thrown away.

Conventions worth matching

  • Comments say why, not what. The codebase leans on explaining the reasoning behind a rule or a guard. Match the density of the file you are in.
  • _ev(kind, **payload) takes kind positionally. Passing kind= in the payload collides with it. Use another key.
  • All randomness goes through Rng. A game must replay identically from its seed and saved RNG state.
  • Refusals are RuleError. Anything else reaches the client as internal, which is the signal that something genuinely broke.
